<Aside type="caution" title="Serverless — les routes doivent être pré-compilées">
Les Workers n'ont pas de système de fichiers persistant. Lacis ne peut pas scanner votre répertoire `routes/` au moment de la requête. Vous devez d'abord exécuter `lacis build` pour générer un manifest de routes.
</Aside>

Cloudflare s'appuie sur la **base d'adaptateur Web** (le même modèle `Request`/`Response` que Bun) : contrairement à Vercel et Netlify, il **streame en direct** — `res.stream()` et les SSE émettent les chunks au fur et à mesure plutôt que de bufferiser toute la réponse.

## Différences avec les autres adaptateurs

| | Node / Bun | Vercel / Netlify | Cloudflare |
|---|---|---|---|
| Config | chaîne / `ServerlessConfig` | `ServerlessConfig` | `ServerlessConfig` |
| Découverte des routes | scan / manifest | Manifest pré-compilé | Manifest pré-compilé |
| Streaming | direct | bufferisé | **direct** |
| `req.platform` | `{}` | `{}` | `{ env, ctx, cf }` |

## Structure du projet

```
my-app/
├── routes/
│   ├── index.ts
│   └── users/
│       └── [id]/
│           └── index.ts
├── worker.ts
├── env.d.ts
└── wrangler.toml
```

## Point d'entrée du Worker

```ts
// worker.ts
import { cloudflareAdapter } from 'lacis/adapters'
import { routes } from './routes/_manifest.js'

export default cloudflareAdapter.createHandler({ routes })
```

<Aside>
`createHandler` initialise les routes, le CORS, les middlewares et les hooks une seule fois au premier `fetch`, puis met le résultat en cache pour les requêtes suivantes dans le même isolate.
</Aside>

## Accéder aux bindings : `req.platform`

Sur Cloudflare, le contexte runtime vit sous `req.platform` :

- `req.platform.env` — vos bindings Worker (KV, D1, R2, Queues, secrets…)
- `req.platform.ctx` — l'`ExecutionContext` (ex. `ctx.waitUntil`)
- `req.platform.cf` — les `IncomingRequestCfProperties` de la requête

```ts
// routes/users/[id]/index.ts
import type { Request, Response } from 'lacis'

export async function GET(req: Request, res: Response) {
  const user = await req.platform.env.MY_KV.get(req.params!.id)
  res.json({ user, country: req.platform.cf.country })
}
```

### Typer `req.platform` avec `env.d.ts`

`req.platform` est vide par défaut et augmenté par déclaration merging. Le template Cloudflare génère un `env.d.ts` pour accéder aux bindings sans `as any` :

```ts
// env.d.ts
/// <reference types="@cloudflare/workers-types" />

interface Env {
  MY_KV: KVNamespace
  MY_DB: D1Database
  // …vos bindings
}

declare module 'lacis' {
  interface PlatformContext {
    env: Env
    ctx: ExecutionContext
    cf: IncomingRequestCfProperties
  }
}
```

```toml
# [[kv_namespaces]]
# binding = "MY_KV"
# id = "..."
```

## Déploiement

<Steps>

1. Ajoutez `lacis build` à votre script de build :

   ```json
   {
     "scripts": {
       "build": "lacis build",
       "deploy": "wrangler deploy"
     }
   }
   ```

2. Générez le manifest et déployez :

   ```bash
   npm run build
   wrangler deploy
   ```

</Steps>

`lacis dev` détecte `wrangler.toml` et lance `wrangler dev` après avoir généré le manifest.

## Notes

- **SSE / `initSSE()`** : comme Bun, Cloudflare décide du streaming de façon synchrone — appelez `res.initSSE()` avant le premier `await` du handler.
- **IP client** : `req.connection.remoteAddress` est renseignée depuis l'en-tête `cf-connecting-ip`.
- **`defaultHeaders`** est supporté (passez-le dans le `ServerlessConfig`).

## Config optionnelle

```ts
export default cloudflareAdapter.createHandler({
  routes,
  maxBodySize: 5_000_000,
  defaultHeaders: { 'X-Powered-By': 'Lacis' },
  cors: { origin: 'https://myapp.com', credentials: true },
})
```
